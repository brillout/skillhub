TLDR

The search manual of Tavily's skills. It sets defaults: advanced search depth unless you need a quick answer, 10 results, and filters such as a date range or a list of domains before asking for more results. Queries use the words a page would use, one per part of the question, and independent searches go out together in one turn. The agent follows leads: when a result names a likely answer, it tests it right away with another search or by extracting the page, and builds lists of candidates from results, not memory. Extract reads up to 20 URLs per call as Markdown, including pages built with JavaScript, retries with a deeper mode for tables or empty pages, and says which pages failed. Map finds the right page on a site; crawl collects a section's pages. Generated answers are summaries to check, never sources, and releases, ownership and official figures must be confirmed on the official domain or repository. If neither the CLI nor the MCP server works, it follows a setup guide that starts without signing in.

Tavily search

Use the tavily_search, tavily_extract, tavily_map and tavily_crawl tools if your tool list has them (some clients add a prefix such as mcp__tavily__). Otherwise run tvly <command> --json directly; there's no need to check for it first. If neither works, follow setup.

Parameters are named as in the API (max_results). The CLI spells them as flags (--max-results) with comma-separated lists (--include-domains sec.gov,reuters.com). For exact parameters, read the tool schema, run tvly <command> --help, or see the API reference.

Search

Use advanced search. Set search_depth to advanced (--depth advanced in the CLI) for every search unless the user needs a fast answer to a simple lookup. It reaches more sources and ranks the passages that match your query.

Write queries for a search engine. Use the names and terms you expect on the page, not the user's whole request. Split a question with several parts into one focused search per part. For a long written report, search each part separately and extract the main sources for each before you write.

Follow your leads. When a result names a likely answer, test it right away: search that name with the other details you know, or extract its page. Keep a lead that fits most details until a source contradicts it; a detail you can't confirm doesn't rule it out. When a search misses, search the details again in their own words before adding names or filters you guessed, and build lists of candidates from results, not memory. When a detail keeps coming back empty, work out what it refers to, such as the role, event or term, and search for that.

Each result's content is already the passages that match your query; print it whole rather than cutting it short.

Batch independent searches. Issue the searches for one step together in one turn, one call each: separate tavily_search calls with MCP tools, or separate Bash calls with the CLI, each holding a single tvly command. MCP calls run in parallel; Bash calls run one after another but still use one turn. Don't add pipes, &, $(...) or other programs to a tvly call, which make the client ask for permission. Put the query in single quotes: tvly search 'Rust 2024 edition release date' --depth advanced --max-results 10 --json.

Ask for 10 results. Set max_results to 10 (--max-results 10). Narrow before you widen. Filters help more than raising max_results further. Use time_range or dates for recent events or a stated period. Use include_domains when the answer lives on an official or named site; it is a hard filter, so search again without it if it doesn't find the page.

Keep large results on disk. When a result is long, such as raw page content or a crawl, save it with -o <file> and read the parts you need with your file-reading tool instead of printing it all. To reuse a file, use the path you wrote; never look for it with a glob over temp folders, which can read another task's files. An MCP result lands straight in your context, so keep those calls small.

Read the results critically. Count independent sources, not results. Treat a generated answer as a summary to check, never as a source.

Extract

Extract returns up to 20 URLs per call as markdown, including pages built with JavaScript.

  • Extract only the few results worth reading. Snippets answer most facts.
  • Extract full pages by default. Pass query (--query) only to isolate one fact on a long page; if the passages come back cut off near what you need, extract again without it.
  • Rerun with extract_depth set to advanced (--extract-depth advanced) when a page is built with JavaScript, the content is in a table, or basic came back empty. Check failed_results every time and say which pages couldn't be read.
  • When you find a direct link to the data itself, such as a CSV or JSON file, download it if you can.

When to stop

  • Stop once two independent sources agree on a fact.
  • Before you answer, close any gap your draft would mark unconfirmed or fill from memory: run one targeted search or reread the saved page.
  • For releases, ownership, official figures and decisions by a named body, confirm on the official domain or repository. A secondary site or a generated answer is not enough.

Hand off the job

When the user wants an in-depth report that needs many sources gathered and weighed, such as an analysis, a comparison across several criteria or an in-depth investigation, use tavily-research instead of your own searches. If it isn't installed, run npx skills add tavily-ai/skills --skill tavily-research and read its SKILL.md first. A single fact or answer to find stays here.
