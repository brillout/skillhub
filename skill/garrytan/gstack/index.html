TLDR

gstack is a large set of role-based skills, and this SKILL.md is only its router. Its rules cover new ideas (office-hours), specs and tickets, plan reviews from CEO, engineering, design and developer-experience angles, bug investigation, QA, code review, shipping and deploys, docs, retros, security audits, PDFs, scraping and iOS testing. A setting called proactive decides how far it goes: off suggests nothing, core, the default, auto-runs four skills, and all invokes whichever skill matches. Browser requests go to browse, which drives the Aside browser with your logged-in sessions first and gstack's own browser otherwise. It routes only to skills that are installed. It starts by running a preamble script, reports its outcome as DONE, DONE_WITH_CONCERNS, BLOCKED or NEEDS_CONTEXT, and sets a voice: direct, no em dashes, no stock AI vocabulary.

Route first

This is the gstack router. Its one job is to send the request to the right skill.

  1. If the request is to test behavior, find bugs, QA or dogfood software → invoke /qa, or /qa-only when the user wants reporting without fixes. These skills select browser, API, CLI, job, worker or webhook surfaces before loading their testing instructions. An API URL does not imply browser testing. An explicit skill request keeps its authority.
  2. If the request is browser interaction, screenshots, or inspecting a page (open a site, take a screenshot, inspect a flow visually) → invoke /browse. Every gstack browser skill (/browse, /qa, /qa-only, /design-review, /canary, /benchmark, /scrape) drives the Aside browser first — the user's real browser with their real logged-in sessions — and falls back to gstack's own browser when Aside is not installed or not running. Route "open the browser" / "import cookies" requests to the fallback-browser skills below only when the user is clearly on that path (Linux, Windows, or Aside closed); on Aside there is nothing to open or import.
  3. Otherwise, route by the rules below. If nothing matches, answer directly.

Best-effort, record which way you routed (never block on it). Set ROUTE_OUTCOME to browse (sent to /browse), routed (sent to another skill), or direct (answered directly, no skill matched), and replace SESSION_ID with the value the skill-start output echoed:

Failures: check the cause, then route. A failing test, error or stack trace shows where a failure surfaces, not its root cause.

  • Cause supplied (the user names a specific cause and a narrow fix): make one read-only check of the evidence it rests on, such as the named file, test or log. If that confirms the cause, make the fix and run the focused test that covers it. If it does not, invoke /investigate before any further tracing or edit.
  • Cause unknown: make one read-only triage pass over the supplied evidence and the directly implicated test and code. Do not reproduce, test hypotheses or search wider. If that pass establishes the root cause and a narrow fix, make the fix and run the focused test that covers it. If the cause, scope or intended behavior is still unclear, invoke /investigate before any broader diagnosis or edit.

Route only to skills in your available-skills list. A rule above whose skill is not listed there is turned off on this install; skip it, never try to invoke it.

When to invoke, and when not to. Invoke when the request matches a skill's purpose: the skill's workflow, checklists and gates beat an ad-hoc answer. Answer directly when no skill matches, for a quick factual question or a small edit the user scoped themselves, and when the user asks for a direct answer instead of a workflow.

If the user opts out of suggestions, run gstack-config set proactive off. If they want every skill suggested, run gstack-config set proactive all. gstack-config set proactive core restores the default (the four core skills only).
