TLDR

text-to-cad runs one local server that builds models and serves a viewer. A model is a decorated Python function with no parameters that returns a build123d shape; its dimensions sit in a plain helper, so each variant is a model of its own with a stable id and page. Running the script is the rebuild: the server replays only what an edit touched, prints what was built and its size, and the open page follows. Files are a separate step, made only when you ask, with a print tolerance for STL or 3MF parts that have fits. After every run the agent reads the build line. It checks numbers you gave with asserts or cad inspect on the measured geometry, never by restating a constant, and checks visible changes with a snapshot from the angle that shows them. A reference you copied from the viewer, such as a face number, is resolved with cad inspect to the code line that made it. It never drops or shrinks a feature you specified just to get a build through, and its reply lists the models changed, files written, checks run and every assumption.

CAD modeling and inspection

A model is a Python function; running its script rebuilds it in text-to-cad's warm server, and the page the person has open updates. Files are exports, made when asked.

Start with the task

Setup and paths

Run the cad command (~/.local/bin/cad where ~/.local/bin is not on your PATH, or where a project's environment puts its own cad first; cad.cmd on Windows). If cad is not found and the CAD app was only just added, its server may still be starting: wait five seconds and run the command again, for up to a minute, before anything else. Otherwise install text-to-cad, outside a sandbox or with its permission:

curl -fsSL https://texttocad.dev/install.sh | sh

On Windows, in PowerShell: irm https://www.texttocad.dev/install.ps1 | iex. Any other failure says what to do, and cad doctor explains the installation.

One server runs for the installation: the first run starts it, every run and every command goes through it, and it serves the viewer. cad status lists its workers and the documents it holds; cad stop stops it. A build cut off by the shell's time limit keeps running in the server; run the same command again and it waits for that build and replays it (cad status shows it). Give a cold build of a large model the shell tool's longest timeout, or run it in the background.

Build every model with cad run. It needs nothing set up: it runs a script in the server's own environment, which holds the library and build123d. A model that needs another package names it at the top of its script, and cad run installs it beside the kernel once, in an environment it keeps for the runs after:

# /// script
# dependencies = ["pandas>=2"]
# ///

For a one-off, cad run --with pandas src/plate.py (repeat --with, or separate requirements with commas; a local folder or wheel works too, its path relative to the working directory, or in the block to the script's folder, and the next run installs it again after an edit). What cannot be installed beside the kernel is refused in one line with uv's reason: change the requirement it names, or, where the network is needed once, run it outside a sandbox or with its permission. In Windows PowerShell, put a version constraint (>=, <) in the block, not on the command line: PowerShell hands it to cad.cmd unquoted, and cmd reads > as a redirection.

Command-line paths, and the paths read_step, read_xbf, read_mesh and export take, are relative to the working directory, as are a model's own file reads. Anchor them on __file__ in code that must run from any folder.

Write a model and run it

A part or an assembly is a function with no parameters, decorated @model (or with its file decorators, never both), that returns a build123d shape. Its dimensions are the arguments of a plain helper function, and each configuration is a @model of its own, with its own id and page; constants several models share live in a module they import. A call builds it and returns its document: a handle with .id, .url, .shape (the built shape) and .export(...). For example, src/bracket.py:

import build123d as bd
from cad import model


def bracket_body(width, thickness, bore):
    body = bd.Box(width, 20, thickness)
    hole = bd.Cylinder(bore / 2, thickness)
    body = body - hole
    body.label = "bracket"
    body.color = "#4a6fa5"
    return body


@model
def bracket():
    return bracket_body(40, 6, 8)


@model
def bracket_wide():
    return bracket_body(60, 6, 8)


if __name__ == "__main__":
    bracket()
    bracket_wide()

Each call the script's __main__ makes prints how its model built, the delta under it (parts, bounds, joints and sequences), its document's id: and its page, view: (the handle's .id and .url). An unchanged rerun prints took ... nothing ran instead. Give the user the page once (Show the model) and use the id for every command after it. The id comes from the script's path and the function's name, or the script's folder and an explicit @model(name="..."), so it is the same run after run, and the open page follows every run. A model's name is its identity within its namespace, the function's name by default, name= gives it another. The namespace is the script's folder; two explicit names in it must differ.

  • Running the script is the rebuild. It writes no file. The server's warm worker for the script replays every operation an edit did not reach, so a comment re-runs nothing and a dimension edit re-runs what reads it (what a run runs). Decoration only declares: keep the calls under if __name__ == "__main__": so other scripts can import the models.
  • @memo marks stages, never parts. The server already replays every kernel call, so mark only a function holding seconds of kernel work that an edit elsewhere leaves alone, such as a whole sub-assembly stage; never a part, never a helper called many times (@memo).
  • An assembly calls its parts. Its body calls each part model and composes its shape (plate().shape), places and labels it, and returns a Compound. Each child builds in the same run and keeps its own document and id. Running a child's script alone leaves the assemblies that use it as they were: run the assembly.
  • import build123d as bd, and use it attribute-style (bd.Box). The import is lazy: the kernel loads on first use, in the worker. from build123d import Box, or a module-level bd.Color(...) or bd.Align default, loads it at that line instead.
  • Colours are sRGB, as a person picks them: part.color = "#4a6fa5", or 0-255 integers. Import metals from bd_materials; assign a native material with part.material = metals.aluminum() (colour and materials).
  • Inputs are read_step, read_xbf and read_mesh in the body, and any file its Python opens, each tracked by its bytes. The clock, environment variables and randomness are not seen: a body is a function of its code and its inputs. Compose project models by calling them, never by reading a file the project exported.
  • References to faces, edges and parts come from cad inspect <id> [ref], and the body picks the same element with build123d's selectors; verify with a snapshot when in doubt (references).
  • A shape with no function (a notebook cell, a REPL) is handed over: model(shape, name="plate") returns the same handle, and no command builds it again.
  • The server never reruns code. A restart reopens every document from the server's cache, as last built. When the cache holds no file of one (deleted by hand, or never saved), the page, cad inspect <id> and cad_show print the command that brings it back (cad run src/bracket.py). Run it.
  • Model units are millimetres, +Z up.
  • An image without a scale sets no fit dimension, and a drawing's units, projection and revision decide how its numbers read. A missing or conflicting dimension that changes the result is the person's to settle; a value chosen in its place is an assumption.

Files, when asked

A file is an action on the document the server holds, never part of the model: no code change and no rebuild, written at once. It holds what the document held when it was written, so a change made after it is in the file only once it is written again. Write one when the person asks for it:

cad export "$ID" STEP/bracket.step STL/bracket.stl GLB/bracket.glb 3MF/bracket.3mf

A project with standing deliverables gets an exports.py that imports its models and calls export(x, path, ...) on each (x a model call's handle); running it rewrites every deliverable (exports). An export takes a document and its destinations, and nothing else: a posed file is a model that returns the posed assembly (posed(arm(), "folded")), and a part on its own is the part's own model. An STL or 3MF for printing a part with fits takes --tolerance MM, about a tenth of its smallest clearance (print tolerance).

The xbf, text-to-cad's own document, is Save As: export one only to share a model without its code, or to compose it in another project with read_xbf. A restart needs none: the server's own cache reopens every document it built, as last built. A vendor STEP is converted to an xbf once (cad export vendor/motor.step vendor/motor.xbf) and read with read_xbf, many times faster than parsing the STEP.

Projects built around exported files

A project can instead revolve around its exported files, but only when the person asks to iterate on the exported file itself or the project already does: an exports.py, a consumer that reads the files (a robot description, a slicer, a drawing pipeline), or a 0.7-era layout, whose runs wrote files. The loop is three steps. The script writes the file on each run, by a file decorator in place of @model (@step("../STEP/bracket.step"), relative to the script), or exports.py or cad export follows the run. Show the file's page, not the model's: it follows the file on disk, updating when a run rewrites the file. Verification reads the file: cad snapshot or cad inspect with its path, or read_step in a check. The costs keep the default the default: each iteration pays the file's translation and the page's re-read, a STEP parsed again; a file names no model, so a ref picked on its page has no made_by and a Quick Edit from it no way back into the code; and the model's page stays the better place to look while editing. Exports tables the triggers and costs.

Pictures

After every run, read its line and the delta under it; a contradiction with what you intended is fixed before anything else. A number the person gave is checked by an assert inside the model's body on what the geometry measures, a bound, a distance or a volume, or by cad inspect, never by restating the constant, and never by code after the call in the model's script (inspection). A derived number they asked for is a check script; neither is ever read off a picture. A structural or appearance change, new parts, placements, colours or a mechanism, gets the snapshots it takes to judge it, usually one from the angle that shows the change, more when a view leaves the question open, and a posed one for a mechanism state; never several angles by habit. For a large assembly, isolate the parts the edit touched or hide what covers them and frame them, instead of drawing the whole model. Resolve a reference with cad inspect only when a prompt names one.

cad snapshot "$ID" tmp/review.png
cad snapshot "$ID" tmp/top.png --camera top --display hidden-line
cad snapshot "$ID" tmp/open.png --pose open

A snapshot draws the document as the viewer does, rendered by OCCT, and writes nothing but the PNG. Its options say how the picture is drawn: camera (--camera top), display, grid, pose (--pose open) and size. It shows arrangement and appearance, not dimensions (snapshots).

Prompt references and inspection

A reference such as 0dc50a92-a21f-5895-a245-ebdeb5352f3b#bracket/face 7 names geometry in a document by the server's own names: the document (a model's id, or a file's absolute path), #, a part or an assembly by the labels on its way from the root (hand/finger.2 is the second component labelled finger in hand), then, after a slash, one element by its name (f:, e:, v:) or its number (face 7). The CAD viewer copies them. When a prompt names one, resolve it with cad inspect:

cad inspect "$ID" "bracket/face 7"

It answers in JSON what the ref names, placed where its occurrence stands: an element's canonical ref, kind, ordinal and name, the kernel's facts (a face's area, centroid, surface, box, radius; an edge's length and endpoints) and made_by, the function, file and line of the code that made it; a part's or an assembly's volume and mass. Edit the code made_by names, or pick the element in the body with build123d's selectors (body.faces().sort_by(bd.Axis.Z)[-1]) matching those facts. A ref resolves in the document as the latest run left it; one that names nothing, or several things where it names one, is refused with what it could mean. The grammar is in references.

A Quick Edit prompt names its document under File: (a path or an id), selected entities under References:, and a snapshot packet as inline JSON or a .snapshot.json path. Save inline JSON to a temporary .snapshot.json, and draw the view the person drew their ink in, ink included:

cad snapshot "$ID" tmp/quick_edit.png --annotation tmp/bracket.snapshot.json --camera authored

Inspect supplied annotations before editing. Without annotations, the captured view is optional context; render it when useful to the request. After editing, run the script and draw it again to check the change (annotations and Quick Edit views).

A reference into a file that is not a document names what the viewer picked in it, in that file's own terms (none is a ref cad inspect resolves):

File Reference Means
URDF, SRDF, SDF /work/arm/arm.urdf#upper_arm the link upper_arm
GLB /work/out/model.glb#n12 the glTF node nodes[12] (0-based, the file's own index)
3MF /work/out/plate.3mf#o2.1 the 2nd <build><item>'s 1st <component> (1-based); #o3 is the 3rd build item
STL the file alone, on File: one mesh: nothing in it is picked

Check the design

A check is a Python script that calls the model and measures what it returns, so it tests the model as it is now. Write one only when the person asks for a dimension, a fit or a mass, or when the change is numeric and the number matters (Pictures):

Copy world_parts and find_part from Opening geometry into the check first. They accumulate parent placements; raw .leaves do not.

from cad.geometry import closest_points

from assembly import assembly

kit = assembly().shape                       # rebuilt (replayed), returned as a tree
plate = find_part(kit, "plate")               # copied into world coordinates
post = find_part(kit, "standoff_left")        # refuses missing or repeated labels
print(plate.bounding_box().size)              # the envelope: not a hole's diameter or a wall's thickness
print(closest_points(plate, post).distance)   # 0: the standoff sits on the plate
  • Measuring is what shows a request's dimensions and clearances. In an assembly, nothing interferes when overlap_volume is 0 for every pair of solids apart from fits named on purpose, and a part meant to rest on another touches it when their closest_points distance is 0. Both describe the parts as built, not a pose (measurements).
  • cad inspect "$ID" <assembly label> weighs an assembly (the label it was given, which is also the root name inspect "$ID" prints): each part's volume times its material's density, and the parts that have no material.
  • A check that fails or cannot decide has shown nothing about the design.
  • A retry that leaves out or shrinks a specified feature (a fillet skipped, a radius reduced) builds a different design from the one asked for.

Hand off

The reply is the person's record of the work: the models made or changed, the files written, the checks run and what they showed, the requirements no check covered, and every assumption or departure from the request.

Show the model

Show the user each model you create or change, and any model or file they ask to see. A file you export is a download: give its path, do not open it. Snapshots and validation don't replace this. Never screenshot the viewer to confirm your own work; review with cad snapshot.

  • If your tools include cad_show (your host may prefix it), call it with the model's id or the file's absolute path, and follow its description for when to call it again. The other tools depend on the host. A host that draws CAD cards or tabs (Claude Desktop, the Codex app) also has cad_view, which reads what the user selected, and cad_screenshot, which shows you what they see, both of a card or tab that is open, for when they ask about it. A text host (Claude Code in a terminal, codex exec) draws nothing: its cad_show opens the model's page in the user's browser and answers with the URL to give them, and it has no view to read. cad_inspect, cad_snapshot and cad_export are on every host. Call only the tools you have, and never say a card shows a model when your host drew none.

  • Otherwise give the user the page's link once: a model's page is the view: line its run prints. For a file, run the CAD Viewer, from any folder:

    cad viewer --json FILE [FILE ...]

    The command ensures this installation's server, registers each file and prints its page, /<id>, then exits. Read each file's url from documents in its one JSON line (never guess the port); the URL carries its token query. A page follows every later run of its model and every rewrite of its file, so share it once. Return that link to the user. If it fails to launch, say so.

Exact selection and measurement need a model's document, an .xbf or a STEP; mesh viewers measure approximately, on triangles.
