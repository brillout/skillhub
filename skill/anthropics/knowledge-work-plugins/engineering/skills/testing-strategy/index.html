TLDR

A one-page testing reference from the engineering plugin of Anthropic's knowledge-work plugins. It starts from the testing pyramid: many fast, focused unit tests, some integration tests and a few slow, high-confidence end-to-end tests. It then suggests a mix by component. API endpoints get unit tests for business logic, integration tests for the HTTP layer and contract tests for their consumers; data pipelines get input validation, transformation and idempotency tests; frontends get component, interaction, visual regression and accessibility tests; infrastructure gets smoke tests, chaos engineering and load tests. Tests should cover business-critical paths, error handling, edge cases, security boundaries and data integrity, and skip trivial getters and setters, framework code and one-off scripts. The result is a test plan listing what to test, the type of test for each area, coverage targets and example test cases, with the gaps in current coverage. It's short guidance with no step-by-step method.

Testing Strategy

Design effective testing strategies balancing coverage, speed, and maintenance.

Testing Pyramid

        /  E2E  \         Few, slow, high confidence
       / Integration \     Some, medium speed
      /    Unit Tests  \   Many, fast, focused

Strategy by Component Type

  • API endpoints: Unit tests for business logic, integration tests for HTTP layer, contract tests for consumers
  • Data pipelines: Input validation, transformation correctness, idempotency tests
  • Frontend: Component tests, interaction tests, visual regression, accessibility
  • Infrastructure: Smoke tests, chaos engineering, load tests

What to Cover

Focus on: business-critical paths, error handling, edge cases, security boundaries, data integrity.

Skip: trivial getters/setters, framework code, one-off scripts.

Output

Produce a test plan with: what to test, test type for each area, coverage targets, and example test cases. Identify gaps in existing coverage.
