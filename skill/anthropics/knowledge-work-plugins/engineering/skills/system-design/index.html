system-design

Use it when
you ask how to architect a system or service, or need help with API design, data modeling or service boundaries
It does
works through five stages: requirements, high-level design, deep dive, scale and reliability, then trade-offs
You get
a structured design document with ASCII or described diagrams, stated assumptions, trade-offs, and what to revisit as the system grows
Unlike
a full design method, it's a one-page checklist of what to cover, with no examples or templates
Part of
the engineering plugin of Anthropic's knowledge-work plugins

TLDR

A short framework the agent follows for design questions. It starts from requirements: what the system does, its scale, latency, availability and cost targets, and constraints such as team size, timeline and existing stack. The high-level design covers a component diagram, data flow, API contracts and storage choices. The deep dive covers the data model, endpoints in REST, GraphQL or gRPC, caching, queues and events, and error handling with retries. Scale and reliability cover load estimates, horizontal or vertical scaling, failover and redundancy, and monitoring. Every decision's trade-offs are made explicit, weighing complexity, cost, team familiarity, time to market and maintainability. The result is a design document with its assumptions spelled out and a note of what to revisit as the system grows.

System Design

Help design systems and evaluate architectural decisions.

Framework

1. Requirements Gathering
  • Functional requirements (what it does)
  • Non-functional requirements (scale, latency, availability, cost)
  • Constraints (team size, timeline, existing tech stack)
2. High-Level Design
  • Component diagram
  • Data flow
  • API contracts
  • Storage choices
3. Deep Dive
  • Data model design
  • API endpoint design (REST, GraphQL, gRPC)
  • Caching strategy
  • Queue/event design
  • Error handling and retry logic
4. Scale and Reliability
  • Load estimation
  • Horizontal vs. vertical scaling
  • Failover and redundancy
  • Monitoring and alerting
5. Trade-off Analysis
  • Every decision has trade-offs. Make them explicit.
  • Consider: complexity, cost, team familiarity, time to market, maintainability

Output

Produce clear, structured design documents with diagrams (ASCII or described), explicit assumptions, and trade-off analysis. Always identify what you'd revisit as the system grows.
