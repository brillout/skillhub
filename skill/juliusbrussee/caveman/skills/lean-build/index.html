lean-build

Use it when
you're adding a feature or an integration and want it complete, but no bigger than what was asked
It does
writes down what must work and what's out of scope, reuses the existing code, and leaves out options, config and polish nobody asked for
You get
a narrow feature working end to end, tested against what was asked, plus a note of any omission that matters
Unlike surgical-patch
which corrects existing behavior in one place, this adds new behavior through all the code involved
Runs
on its own, whenever the agent sees a task that fits; it's a short list of rules, not a step-by-step guide

Skill 12 of 16 in the Caveman bundle · Before it: investigate-first · After it: surgical-patch

TLDR

The agent derives acceptance criteria and explicit non-goals from your request and the repository. It follows the feature from where it starts through every part of the code involved and builds one complete path, rather than cramming it into one file or a local patch. It hooks into existing code where that fits, and refactors only when patching would duplicate behavior or blur which code is responsible for what. Extra modes, options, configuration and polish stay out unless the criteria need them, and any new dependency, service or migration needs a stated reason. It runs the new path, runs a focused test, and stops as soon as the criteria pass.

Lean build

Native Core's architecture-first simplicity remains mandatory. Turn feature into complete narrow outcome fitting system.

  • Derive observable acceptance and explicit non-goals from request and repository.
  • Trace entry point through layers owning invariants.
  • Deliver coherent end-to-end path across responsible layers; never force work into one file, direct expression, or local patch.
  • Reuse fitting seam. Refactor when patching duplicates behavior, weakens ownership, or hides root cause.
  • Omit modes, providers, config, extensibility, and polish unless acceptance needs them.
  • Add surface, dependency, service, config, or migration only for lifecycle design or acceptance; state material tradeoff.
  • Keep work runnable; preserve Core safety.

Exercise path. Run focused proof. Stop when acceptance passes. Report only material omissions and trigger.
