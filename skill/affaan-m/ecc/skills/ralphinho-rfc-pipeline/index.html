ralphinho-rfc-pipeline

Use it when
a feature is too big for one agent pass and you have an RFC to split among several agents
It does
breaks the RFC into a graph of dependent work units, runs each through research, plan, build, tests and review, then merges them through a queue
You get
an execution log, a scorecard per unit, a snapshot of the dependency graph and an integration risk summary
Keep in mind
it's a one-page outline of stages and rules, with no scripts or prompts of its own

TLDR

An outline for running a large feature as many agent-sized pieces. The RFC is decomposed into a DAG, a graph of work units in which each unit lists what it depends on, its scope, acceptance tests, a risk level and a rollback plan. Units fall into three tiers, from isolated file edits with deterministic tests to schema, auth, performance or security changes. Each unit goes through research, an implementation plan, implementation, tests, review and a merge-ready report. Merges go through a queue: never merge a unit whose dependencies failed, always rebase unit branches on the latest integration branch, and rerun integration tests after each merge. A stalled unit is pulled from the queue, its findings saved, its scope narrowed, and it's retried with the new constraints. The run ends with a final verification of the whole system.

Ralphinho RFC Pipeline

Inspired by humanplane style RFC decomposition patterns and multi-unit orchestration workflows.

Use this skill when a feature is too large for a single agent pass and must be split into independently verifiable work units.

Pipeline Stages

  1. RFC intake
  2. DAG decomposition
  3. Unit assignment
  4. Unit implementation
  5. Unit validation
  6. Merge queue and integration
  7. Final system verification

Unit Spec Template

Each work unit should include:

  • id
  • depends_on
  • scope
  • acceptance_tests
  • risk_level
  • rollback_plan

Complexity Tiers

  • Tier 1: isolated file edits, deterministic tests
  • Tier 2: multi-file behavior changes, moderate integration risk
  • Tier 3: schema/auth/perf/security changes

Quality Pipeline per Unit

  1. research
  2. implementation plan
  3. implementation
  4. tests
  5. review
  6. merge-ready report

Merge Queue Rules

  • Never merge a unit with unresolved dependency failures.
  • Always rebase unit branches on latest integration branch.
  • Re-run integration tests after each queued merge.

Recovery

If a unit stalls:

  • evict from active queue
  • snapshot findings
  • regenerate narrowed unit scope
  • retry with updated constraints

Outputs

  • RFC execution log
  • unit scorecards
  • dependency graph snapshot
  • integration risk summary
