TLDR

A reference for automating release documentation. Conventional Commits is a commit message format, type(scope): description, where the type (feat, fix, perf and so on) decides which changelog section a change lands in and whether the major, minor or patch number goes up; a ! or a BREAKING CHANGE footer marks a breaking change. Keep a Changelog is a changelog layout with an Unreleased section and Added, Changed, Deprecated, Removed, Fixed and Security headings under each version. The SKILL.md itself holds commit message examples, the body of an internal release notes template (summary, highlights, breaking changes, upgrade guide, known issues, updated dependencies) and do's and don'ts. The commit type table, the version rules and most of the changelog example sit in its reference file, which also gives six ways to automate it: conventional-changelog tooling with commitlint and a husky commit hook, standard-version, semantic-release for fully automated releases, a GitHub Actions release workflow, git-cliff, and commitizen for Python projects, plus a GitHub release notes template.

Best Practices

Do's
  • Follow Conventional Commits - Enables automation
  • Write clear messages - Future you will thank you
  • Reference issues - Link commits to tickets
  • Use scopes consistently - Define team conventions
  • Automate releases - Reduce manual errors
Don'ts
  • Don't mix changes - One logical change per commit
  • Don't skip validation - Use commitlint
  • Don't manual edit - Generated changelogs only
  • Don't forget breaking changes - Mark with ! or footer
  • Don't ignore CI - Validate commits in pipeline
