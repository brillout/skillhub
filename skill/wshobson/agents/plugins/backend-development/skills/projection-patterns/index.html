projection-patterns

Use it when
you have an event-sourced system and need query-friendly views, dashboards or search indexes built from its events
Terms
a projection turns a stream of events into a read model, a table or index shaped for queries; a checkpoint records the last event applied
It does
explains four projection types, live, catch-up, persistent and inline, and nine do's and don'ts, such as idempotent projections so replays are safe
You get
async Python templates for a projector with checkpoints and rebuilds, an order summary, an Elasticsearch search index, daily sales totals and a multi-table projection

TLDR

In CQRS with event sourcing, changes are stored as events and reads come from separate read models; this skill covers that read side. The SKILL.md shows the architecture (event store, projector, read model) and four projection types: live from a subscription for current state, catch-up over history to rebuild, persistent with a stored checkpoint to resume after a restart, and inline in the write's transaction for strong consistency. Its rules: make projections idempotent so replays are safe, use transactions for multi-table updates, store checkpoints, monitor lag and plan for rebuilds; keep projections independent, handle and alert on errors, process events in order and denormalize for the queries you need. A reference file holds the templates, in async Python, with asyncpg for Postgres: a base Projection class and a Projector that runs each projection from its checkpoint and can rebuild one from scratch, an order summary projection, a product search projection into Elasticsearch, a daily sales aggregate that subtracts refunds, and a customer activity projection across several tables.

Projection Patterns

Comprehensive guide to building projections and read models for event-sourced systems.

When to Use This Skill

  • Building CQRS read models
  • Creating materialized views from events
  • Optimizing query performance
  • Implementing real-time dashboards
  • Building search indexes from events
  • Aggregating data across streams

Best Practices

Do's
  • Make projections idempotent - Safe to replay
  • Use transactions - For multi-table updates
  • Store checkpoints - Resume after failures
  • Monitor lag - Alert on projection delays
  • Plan for rebuilds - Design for reconstruction
Don'ts
  • Don't couple projections - Each is independent
  • Don't skip error handling - Log and alert on failures
  • Don't ignore ordering - Events must be processed in order
  • Don't over-normalize - Denormalize for query patterns
