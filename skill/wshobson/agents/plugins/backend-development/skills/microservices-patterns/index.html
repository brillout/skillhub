microservices-patterns

Use it when
you're splitting a monolith into services, drawing service boundaries, or designing how services talk to each other and survive each other's failures
It does
gives the agent patterns for cutting services, calling them directly or through events, giving each its own data, and staying up when one fails
You get
designs along those patterns; it adds no steps or files of its own, and a reference file holds Python examples
Terms
a saga is a chain of local transactions with compensating undo steps; a circuit breaker stops calling a failing service for a while

TLDR

A reference, not a workflow. It names three ways to cut services: by business capability (orders, payments, inventory), by subdomain, where each bounded context from domain-driven design becomes a service, and the strangler fig pattern, which moves features out of a monolith gradually behind a proxy. Services talk synchronously over REST, gRPC or GraphQL, or asynchronously through Kafka, RabbitMQ or SQS. Each service owns its database, and transactions that span services become sagas with eventual consistency. Resilience comes from circuit breakers, retries with exponential backoff and bulkheads, which isolate resources so one failure stays contained. The reference file shows each in Python: services that publish events, a FastAPI gateway that combines several services' data behind circuit breakers and tolerates partial failures, an HTTP client with retries and timeouts, an event bus on Kafka, an order-fulfillment saga that runs compensations when a step fails, and a circuit breaker class with closed, open and half-open states.

Microservices Patterns

Master microservices architecture patterns including service boundaries, inter-service communication, data management, and resilience patterns for building distributed systems.

When to Use This Skill

  • Decomposing monoliths into microservices
  • Designing service boundaries and contracts
  • Implementing inter-service communication
  • Managing distributed data and transactions
  • Building resilient distributed systems
  • Implementing service discovery and load balancing
  • Designing event-driven architectures

Core Concepts

1. Service Decomposition Strategies

By Business Capability

  • Organize services around business functions
  • Each service owns its domain
  • Example: OrderService, PaymentService, InventoryService

By Subdomain (DDD)

  • Core domain, supporting subdomains
  • Bounded contexts map to services
  • Clear ownership and responsibility

Strangler Fig Pattern

  • Gradually extract from monolith
  • New functionality as microservices
  • Proxy routes to old/new systems
2. Communication Patterns

Synchronous (Request/Response)

  • REST APIs
  • gRPC
  • GraphQL

Asynchronous (Events/Messages)

  • Event streaming (Kafka)
  • Message queues (RabbitMQ, SQS)
  • Pub/Sub patterns
3. Data Management

Database Per Service

  • Each service owns its data
  • No shared databases
  • Loose coupling

Saga Pattern

  • Distributed transactions
  • Compensating actions
  • Eventual consistency
4. Resilience Patterns

Circuit Breaker

  • Fail fast on repeated errors
  • Prevent cascade failures

Retry with Backoff

  • Transient fault handling
  • Exponential backoff

Bulkhead

  • Isolate resources
  • Limit impact of failures
