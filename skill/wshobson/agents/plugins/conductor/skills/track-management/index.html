TLDR

Conductor, a plugin in the same repo, keeps a project's context in a conductor/ folder and splits work into tracks; this skill is its guide to tracks. Creating one means gathering requirements by Q&A, writing spec.md (functional and non-functional requirements, testable acceptance criteria, what's in and out of scope, dependencies, risks and open questions) and plan.md (phases of tasks, each ending in verification tasks, with a checkpoint table), then registering it in tracks.md with a metadata.json and an index. During implementation, tasks are marked as they go and completed ones record their commit SHA; each phase needs its verification and an approved checkpoint before the next. On completion, the track is marked done, product.md and tech-stack.md are updated if features or dependencies changed, and the track is archived rather than deleted. Tracks should take one to five days, with two to four phases and 8–20 tasks; it lists signs of tracks too large or too small, how to record hard, soft and external dependencies, and phase patterns for features, bug fixes (start with a failing test) and refactors (start with characterization tests). The SKILL.md holds only ten best practices; the rest is in a reference file.

Track Management

Guide for creating, managing, and completing Conductor tracks - the logical work units that organize features, bugs, and refactors through specification, planning, and implementation phases.

When to Use This Skill

  • Creating new feature, bug, or refactor tracks
  • Writing or reviewing spec.md files
  • Creating or updating plan.md files
  • Managing track lifecycle from creation to completion
  • Understanding track status markers and conventions
  • Working with the tracks.md registry
  • Interpreting or updating track metadata

Detailed patterns and worked examples

Detailed pattern documentation lives in references/details.md. Read that file when the navigation tier above is insufficient.

Best Practices

  1. One track, one concern: Keep tracks focused on a single logical change
  2. Small phases: Break work into phases of 3-5 tasks maximum
  3. Verification after phases: Always include verification tasks
  4. Update markers immediately: Mark task status as you work
  5. Record SHAs: Always note commit SHAs for completed tasks
  6. Review specs before planning: Ensure spec is complete before creating plan
  7. Link dependencies: Explicitly note track dependencies
  8. Archive, don't delete: Preserve completed tracks for reference
  9. Size appropriately: Keep tracks between 1-5 days of work
  10. Clear acceptance criteria: Every requirement must be testable
