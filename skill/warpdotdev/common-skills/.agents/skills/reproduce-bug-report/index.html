reproduce-bug-report

Use it when
a GitHub issue, Linear ticket, support report or prompt describes a visible bug: rendering, layout, settings, onboarding or another interaction
It does
extracts the reported and expected behavior, steps and environment, then sends one cloud agent, or several with distinct hypotheses, to run the app and try it
You get
one summary: confirmed, partially confirmed, not reproduced or blocked, what each variant tested, exact steps, environment and versions, and a screen recording with screenshots
Needs
Oz cloud agents with computer use, launched through Warp's run_agents tool
Keeps
secrets and account details out of recordings and reports; agents don't sign in or post anywhere unless authorized, except the recording to a Slack thread they're given

Needs Warp's Oz cloud agents with computer use, launched through Warp's run_agents tool.

TLDR

The parent agent doesn't try the bug itself unless you ask; it briefs cloud agents that can run the app and record the screen. It first decides whether the skill fits: purely backend, CI or build problems are out of scope, and a report that needs credentials or private state is reported as blocked rather than guessed at. One agent follows the report's steps exactly; others test variants such as a different OS, a fresh versus existing setup, or a stable versus dev build, and when steps are missing one traces UI strings and settings in the code to choose a likely path. Each installs the version closest to the reporter's and records any fallback, saves a recording, numbered screenshots and a manifest to its own directory, and tries at most two targeted variations if the bug doesn't appear. Given a Slack thread, it posts the recording back there, and to no other channel. A repository can add a reproduce-bug-report-local skill for its own setup. The parent waits for every agent, then summarizes what was tested, the evidence, the findings and one next step.
