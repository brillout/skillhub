saga

Use it when
a medium-to-large feature should be built mostly autonomously, or you're resuming a saga from its directory
It does
asks multiple-choice questions until no requirement is open, splits the work into milestones and tasks with validation criteria, then delegates tasks to parallel workers
You get
the feature built on saga branches and integrated milestone by milestone, plus a spec tree and PROGRESS.md log under ~/.sagas/, outside the repo
You step in
to approve the spec, on blockers the spec can't settle, and for final acceptance
Needs
subagents, through Warp's run_agents tool, with a git worktree for each local worker, and an ask_user_question tool for its multiple-choice questions

TLDR

The bet behind a saga is that if every task's validation criteria are tight enough to be a contract, workers can run in parallel and check themselves. Phase 1 is planning with you: the agent creates a saga directory under ~/.sagas/, works out what kind of program it is, whether computer use is available and which build and test commands run, then asks multiple-choice questions until scope, edge cases and the acceptance bar are settled. It writes saga-level exit criteria, then SAGA.md, a MILESTONE.md per milestone and a file per task, and waits for your approval. Phase 2 delegates: the orchestrator writes no feature code, launching each milestone's independent tasks as one batch, each local worker in its own worktree on a branch named saga/<name>/m<M>t<T>-<slug>. Workers validate in a loop, commit or hand off a patch before removing their worktree, and report compactly; PROGRESS.md records run IDs and status so a fresh agent can resume. Phase 3 checks the exit criteria with the strongest method available and asks you to accept or report issues, which become new tasks.
