write-product-spec

Use it when
you want a feature's behavior pinned down in writing before an agent builds it, as a product spec or PRD
It does
asks you for missing context and for a Figma mock when there's UI, then writes the behavior as numbered rules that can each be tested
You get
specs/<id>/PRODUCT.md: a short summary and an exhaustive Behavior section, with no implementation details and no test plan
Next step
write-tech-spec, which plans the implementation and the tests from these rules

Skill 2 of 5 in the Warp spec workflow bundle · Before it: spec-driven-implementation · After it: write-tech-spec

TLDR

A product spec here describes behavior only from the side of whoever uses the feature: the person in the app, code reading a data model, callers of an API, or a developer running a CLI. It names no internal types, modules or algorithms. The Behavior section carries the spec: the happy path, every visible state and transition, all inputs, empty, error, loading and cancelled states, edge cases such as offline, timeouts, races and focus loss, keyboard and accessibility, and what must never regress. Everything else stays thin: a summary of one to three sentences, and Problem, Goals, Figma or Open questions only when they add something. Testing is left out on purpose; it belongs in TECH.md, which write-tech-spec writes from these rules. The folder is named after a Linear ticket, a GitHub issue or a short feature name, and a new ticket is filed only if you ask. Length follows the feature: no spec for trivial fixes, about 30 to 60 lines for a small feature. It's written for Warp, and its worked example specifies Markdown tables in Warp's block list.
