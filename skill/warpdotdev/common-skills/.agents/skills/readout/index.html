readout

Use it when
you say "write this up" mid-investigation, or want a readable explainer such as how a server processes webhook events
It does
asks two to four scoping questions with concrete options, then hands a short brief to one local child agent that mines the conversation or researches the code
You get
~/.readouts/<date>-<topic>.html built from a shared template, with linked and embedded code references, plus a regenerated index.html of every readout
Modes
snapshot, from what the conversation already found; research, starting fresh from the codebase
Runs
as a side task: the main agent launches the child and carries on, then relays the file path

TLDR

A readout is meant to be read weeks later by someone with none of the original context. The main agent's part is small: sharpen the scope, always settling depth and audience but skipping questions when the request is already specific, then write a brief of 10 to 20 lines with pointers rather than pasted findings: the questions to answer, what to cover and exclude, repo paths, and each repo's URL and commit for code links. One child agent, launched locally through Warp's run_agents tool so the file lands on your machine, does the writing. In snapshot mode it searches the parent conversation by run ID and verifies file references; in research mode it traces the real code paths and grounds claims in file:line references, separating verified from inferred. It follows the skill's doc guide and HTML template, embeds snippets and refreshes the index with bundled Python scripts, and opens the file unless the machine is headless. Without subagents, the main agent writes the document itself.
