spec-driven-implementation

starting a large, risky or ambiguous feature that an agent will build, such as one around 1k+ lines

Skill 1 of 5 in the Warp spec workflow bundle · After it: write-product-spec

Only works inside its bundle: Loads write-product-spec, write-tech-spec and implement-specs for its three main steps; on its own it only decides whether specs are needed and files the Linear issue. Install Warp spec workflow instead.

Needs the Linear MCP server: it creates a Linear issue before writing specs when none exists.

TLDR

Warp's process for features where written specs will improve an agent's work and the review. Specs are for substantial work: product or architectural ambiguity, around 1k+ lines, deep or cross-cutting changes, risky behavior changes. Small bug fixes, straightforward refactors and narrow UI tweaks usually skip them. Specs live in specs/<Linear ticket>/, and if no Linear issue exists the agent creates one first with the Linear MCP tools, asking you when the team or labels aren't obvious. write-product-spec writes PRODUCT.md, the user-facing behavior, and the agent asks for a Figma mock when there's UI. write-tech-spec writes TECH.md when the work spans subsystems or has trade-offs worth reviewing, possibly after an end-to-end prototype. implement-specs builds from them once they're approved. For large features it may offer PROJECT_LOG.md and DECISIONS.md to record explored paths and decisions. When the implementation drifts, the specs are updated with the code, in the same PR whenever practical, and the work is verified against them with unit and integration tests, and walkthrough recordings or screenshots for UI-heavy work.
