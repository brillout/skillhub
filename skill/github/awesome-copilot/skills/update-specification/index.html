requirements changed or the code moved on, and a spec file in /spec/ needs to catch up

TLDR

The update counterpart of create-specification. You give it a spec file, and it brings it in line with new requirements or changes to the existing code. The spec is written for AI readers: precise, explicit language, requirements kept apart from constraints and recommendations, no idioms or metaphors, every acronym defined, examples and edge cases included, and a document that stands on its own. The template's sections are purpose and scope, definitions, requirements, interfaces and data contracts, acceptance criteria, test automation strategy, rationale, dependencies, examples and edge cases, validation criteria and related specs. Requirements carry prefixed IDs such as REQ-001, SEC-001, CON-001, GUD-001 and PAT-001, acceptance criteria use Given-When-Then where it fits, and dependencies say what is needed, such as an OAuth 2.0 library, rather than a package and version. Front matter holds the title, version, creation and update dates, owner and tags. Like create-specification, the test section suggests MSTest, FluentAssertions and Moq for .NET apps and GitHub Actions for CI.

Update Specification

Your goal is to update the existing specification file ${file} based on new requirements or updates to any existing code.

The specification file must define the requirements, constraints, and interfaces for the solution components in a manner that is clear, unambiguous, and structured for effective use by Generative AIs. Follow established documentation standards and ensure the content is machine-readable and self-contained.

Best Practices for AI-Ready Specifications

  • Use precise, explicit, and unambiguous language.
  • Clearly distinguish between requirements, constraints, and recommendations.
  • Use structured formatting (headings, lists, tables) for easy parsing.
  • Avoid idioms, metaphors, or context-dependent references.
  • Define all acronyms and domain-specific terms.
  • Include examples and edge cases where applicable.
  • Ensure the document is self-contained and does not rely on external context.

The specification should be saved in the /spec/ directory and named according to the following convention: [a-z0-9-]+.md, where the name should be descriptive of the specification's content and starting with the highlevel purpose, which is one of [schema, tool, data, infrastructure, process, architecture, or design].

The specification file must be formatted in well formed Markdown.

Specification files must follow the template below, ensuring that all sections are filled out appropriately. The front matter for the markdown should be structured correctly as per the example following:
