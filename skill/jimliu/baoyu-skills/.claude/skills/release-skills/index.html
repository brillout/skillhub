release-skills

Use it when
a Node.js, Python, Rust, Claude plugin or plain VERSION-file project is ready for a new version
It does
reads the commits since the last tag, picks a semantic version bump, updates the version file and changelogs, commits and creates an annotated tag
You get
updated changelogs in every language your repo keeps, such as CHANGELOG.zh.md, a release commit, a tag and, if you agree, a GitHub Release
When it asks
just before the release commit, for the version, pushing and the GitHub Release; by then it has already committed pending changes per module and written the changelogs
Watch out
it triggers on "push" too, and runs all its release steps even when you only ask to push uncommitted changes
Needs
git, and the gh CLI signed in for GitHub Releases
Origin
the release tool baoyu-skills uses on itself, kept in its .claude folder rather than among its published skills

It also triggers on "push", and then runs its whole release process even when you only meant to push.

TLDR

It detects the version file (package.json, pyproject.toml, Cargo.toml, marketplace.json or VERSION) and every CHANGELOG, HISTORY or CHANGES file, telling each one's language from its filename suffix. A breaking change means a major bump, a feat commit a minor one and anything else a patch, unless you force one with a flag. Each changelog gets entries written in its own language rather than translated, with (by @username) after changes merged from anyone but the repo owner. Changes are grouped by skill or module, as in a repo of skills/<name> folders, committed separately with conventional commit messages, and the READMEs checked for options or examples that need updating. A dry run previews everything without changing anything, and a backfill mode creates missing GitHub Releases for existing tags from their changelog sections, without bumping versions. A .releaserc.yml can override the detected files, changelog sections and tag format, or hand packaging and publishing to your own hooks.
